Overview

Daawa is a Software-as-a-Service (SaaS) platform designed to simplify event invitation, guest management, and check-in processes for a diverse range of event organizers. It solves the problem of inefficient, manual, and often costly traditional event management by providing a centralized digital solution. Daawa is for individuals planning personal events (weddings, parties), organizations (mosques, non-profits, schools), and businesses (workshops, corporate events) who need a modern, streamlined way to manage their attendees. Its value lies in offering flexible guest acquisition (self-registration links, direct invites), customizable digital passes (PDF, Apple/Google Wallet), integrated check-in, and full support for English and Arabic (RTL) users, all under a usage-based pricing model. A key feature is the ability for organizers to explore and set up their event in a "Draft" state before committing to payment and activation.

Core Features

Event Creation & Management (Draft & Active States):

What it does: Allows organizers to define event details (name, date, venue, etc.), select a guest capacity tier, configure a self-registration form, and design a digital pass template. Organizers can fully set up their event in a "Draft" state. Upon submission and manual admin activation (after payment), the event becomes "Active," unlocking guest-facing features.

Why it's important: Provides a risk-free way for organizers to explore the platform. Clearly defines event parameters and pricing. Enables core event setup.

How it works: Organizer fills out forms in the portal. Data is saved via API. Admin interface allows activation.

Guest Acquisition (+N Guest Management):

What it does: Supports two primary methods:

Self-Registration Link: Generates a unique link to an online form where guests can register themselves and their additional "+N" guests (number specified by organizer).

Direct Email Invites: Allows organizers to manually add/import guests and send personalized email invitations containing a link to their digital pass. Organizers can specify "+N" for these invites too. All primary and "+N" guests count towards the event's paid capacity.

Why it's important: Offers flexibility for different event types (open vs. invite-only). Manages group invitations efficiently.

How it works: Backend generates unique links. Form submissions and manual entries are processed via API, adding guests to the event list, respecting capacity and "+N" limits.

Digital Pass Generation (Unified Design):

What it does: Organizers design a single template (background, logo, accent color, PDF font). The system then generates personalized digital passes for each primary guest in PDF, Apple Wallet, and Google Wallet formats. Passes include event details, a unique QR code, and names of accompanying "+N" guests.

Why it's important: Provides guests with a convenient, modern way to access event info and their entry credential. Ensures consistent branding.

How it works: Design configuration saved via API. Backend services (using Puppeteer, passkit-generator, Google Pay API) generate passes on demand using the template and guest data.

Web-Based Check-in Module:

What it does: A mobile-responsive web page accessible by event staff. Allows staff to scan guest QR codes (via device camera) or manually look up guests. Displays guest details, expected "+N" guests, and allows staff to mark primary and specific "+N" guests as checked-in.

Why it's important: Facilitates smooth and efficient event entry. Provides real-time attendance tracking for organizers. No native app installation required for staff for MVP.

How it works: Web module interacts with check-in APIs. Camera access via browser getUserMedia. Scanned data sent to API for validation and recording check-ins.

Multilingual Support (English & Arabic with RTL):

What it does: All user interfaces (Organizer Portal, Guest Portal, Check-in Module, Admin Interface) and communications are available in both English and Arabic, with full Right-to-Left (RTL) layout support for Arabic.

Why it's important: Caters to a key target market, enhancing usability and accessibility.

How it works: Frontend uses i18n libraries. Backend APIs support locale information. UI styling (Tailwind/Daisy UI) handles RTL.

User Experience

User Personas:

Event Organizer: Varies in tech-savviness. Needs efficiency, control, and a professional output. Uses portal for setup and management.

Guest: Wide range of tech comfort. Needs clear information and easy interaction (registration, accessing pass).

Check-in Staff: Needs a fast, simple tool for entry management on event day, used on mobile devices.

Platform Administrator: Needs clear tools for event activation and basic oversight.

Key User Flows:

Organizer Onboarding & Event Creation (Draft): Register -> Login -> Create Event -> Fill Details -> Select Tier -> Design Card -> Configure Form -> Save Draft.

Event Activation: Organizer Submits Draft -> Admin Reviews -> Admin Marks Paid & Activates -> Organizer Notified.

Guest Self-Registration: Organizer Shares Link -> Guest Clicks Link -> Fills Form (incl. +N) -> Submits -> Receives Confirmation & Pass Download Options.

Direct Invitation: Organizer Adds Guest Manually (incl. +N) -> Sends Email Invite -> Guest Receives Email -> Clicks Link to Access Pass/Portal.

Event Check-in: Staff Logs into Web Module -> Scans Guest QR (or Manual Lookup) -> Views Guest/+N Info -> Marks Present Guests -> Guest Enters.

UI/UX Considerations:

UI Stack: React/Next.js with Tailwind CSS and Daisy UI for consistent, responsive, and maintainable interfaces.

Simplicity & Clarity: Prioritized in all interfaces. Minimize cognitive load.

Visual Feedback: Clear indicators for actions, statuses, errors (using Daisy UI components).

Mobile-First: For Guest Portal and Check-in Module. Organizer portal is responsive.

Accessibility (A11y): Strive for WCAG 2.1 AA (color contrast, keyboard nav).

RTL: All UI elements and layouts must adapt correctly for Arabic.

Card Designer: Unified, simple visual editor with previews for PDF/Wallet.

Check-in Module: Optimized for speed and ease of use on mobile browsers.

Technical Architecture

System Components:

Frontend Web Application (Daawa Portal): (React/Next.js, Tailwind CSS, Daisy UI) Serves Organizer Portal, Guest Portal, Admin Interface, and Web-Based Check-in Module.

Backend API Server (Daawa API): (NestJS, Node.js) Exposes RESTful APIs for all platform functionalities. Modular design (Auth, Events, Guests, Passes, Check-in, Notifications, Admin).

Database: (PostgreSQL) Stores all persistent data (users, events, guests, configurations, etc.).

Pass Generation Service: (Integrated within NestJS Backend) Uses Puppeteer (for PDF), passkit-generator (for Apple Wallet), and Google Pay API Client to create digital passes.

Notification Service: (Integrated within NestJS Backend) Handles sending emails (initially). Hooks for future SMS/WhatsApp.

Cloud Storage: (e.g., AWS S3, Google Cloud Storage) For storing user-uploaded assets (logos, background images for cards) after processing.

Content Delivery Network (CDN): For serving static assets (frontend bundles, processed images) globally.

Data Models (Core - PostgreSQL):

Users (id, name, email, password_hash, role [Organizer, Admin, Staff], preferred_language)

Events (id, organizer_id, name, status [Draft, Pending, Active, Archived], tier_id, capacity_limit, primary_language, default_plus_n, design_config [JSONB], form_config [JSONB], event_details [JSONB: type, dates, venue])

Tiers (id, name, guest_limit, price, currency)

Guests (id, event_id, primary_guest_id [FK to self, NULL if primary], name, email, phone, invite_status, rsvp_status, checkin_status, checkin_timestamp, checked_in_by_user_id, allowed_plus_n_override, custom_field_answers [JSONB], is_primary)

CheckinRecords (id, guest_id [FK to Guests, Primary Guest], event_id, checkin_timestamp, checked_in_by_user_id, present_additional_guest_ids [JSONB/Array])

APIs and Integrations:

Internal RESTful APIs: Between Frontend and Backend (as detailed in prior PRD v1.8, Section 4.12). All functionalities exposed via these APIs. Documented with Swagger/OpenAPI.

External APIs (Consumed by Backend):

Google Pay API for Passes (for Google Wallet pass generation).

(Future) SMS Gateway API (e.g., Twilio).

(Future) WhatsApp Business API.

(Future) Payment Gateway APIs (for automated activation).

Risks and Mitigations

Technical Challenges:

Cross-Browser Camera Access (Web Check-in): Ensuring consistent getUserMedia behavior. Mitigation: Thorough testing on target mobile browsers, provide clear user guidance if permissions are tricky.

Wallet Pass Generation Complexity (Apple/Google): Specific requirements, certificate management. Mitigation: Allocate dedicated time for setup and testing, follow documentation meticulously. Use recommended libraries.

PDF Generation from HTML/CSS (Puppeteer): Performance, font rendering, complex layouts. Mitigation: Start with simple PDF templates, optimize server-side rendering, thorough testing of EN/AR fonts.

RTL Implementation: Ensuring all Daisy UI components and custom layouts adapt correctly. Mitigation: Continuous RTL testing throughout development, use Tailwind's RTL utilities.

Figuring out the MVP that we can build upon:

Scope Creep: Tendency to add "just one more thing." Mitigation: Strict adherence to the defined MVP features in Phase 1. Defer non-essentials.

Balancing Simplicity vs. "Enough" Customization: Especially for card design. Mitigation: Launch with simple options (BG, logo, accent, PDF font). Gather user feedback quickly to inform Phase 2 enhancements.

Resource Constraints:

Development Time/Budget: Building all features to a high quality takes time. Mitigation: Prioritize MVP ruthlessly. Modular backend helps if different parts can be developed somewhat in parallel (if team size allows). Clear task breakdown from the roadmap.

Specialized Skills (e.g., NestJS, Pass Generation): Mitigation: Ensure team has or can acquire necessary skills, or allocate budget for expert consultation if needed.
